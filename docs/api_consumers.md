# API consumers (Phase 0 inventory)

Read-only audit, 2026-11-03. Sources:

- **Web app:** `ut_landing/src` (Vite SPA, branch `perf/phase-0-audit` in `ut_landing`).
- **Flutter app:** `urban_tanker_app/lib`, branch `ui-redesign`. The audit reflects the **uncommitted working tree** (the client is mid-refactor into `lib/services/api/*`), so re-check it after that work lands.
- **Backend:** `ut_landing/backend/src`. Each mismatch below was checked against the route file.

## Conventions

- Paths are relative to the API base URL, which is `/api` in both clients (`VITE_API_BASE_URL` on web, `API_BASE_URL` default `https://urban-tanker-backend.onrender.com/api` on Flutter). `/customer/orders` means `/api/customer/orders`.
- "Pagination" is what the client sends or reads. "Caching/polling" covers client-side caches, timers and refresh loops.
- The backend has **no** `Cache-Control`, `ETag` handling, or 429/`Retry-After` handling on API responses; neither client uses `If-None-Match` today.

## Summary

- Only `GET /customer/orders` and `GET /vendor/orders` paginate, and only with an offset and `pageSize` contract that the client already reads. Every other list is unpaged, and admin lists are fetched whole and paged on the client.
- Polling is limited (customer tracking falls back to 60 s polling only when the socket is down; public tracking polls every 30 s; vendor GPS posts every 15 s while the Orders view is open).
- Several clients fan out: admin entity managers mount four lists each, "mark all read" sends one PATCH per notification, the Flutter vendor offline flush sends one POST per queued item.
- Known client bugs found during the audit are listed in each file's Cross-cutting section (e.g. the partner form sends empty `partnerType`/`availability`; the pricing screen hard-codes `isActive: true`).

React Query retries queries only on HTTP 5xx, twice (providers/AppProviders.tsx:6-7). Mutations are not retried. On 401, a single-flight refresh runs and the request is retried once (client.ts:38-60, 113-115); /auth/* paths are excluded.

### auth

Flows that must stay unchanged (as they exist now):

- Password sign-in: `AppController.signIn` trims the credential; `AuthApi.login` sends `{email, password}` when the credential contains "@", otherwise `{username, password}`, to `POST /auth/login` with `retry: false`. The response is saved through `_saveAuthResult`.
- Email+password sign-up: `POST /auth/signup` with `email, password, name, phone, role: 'customer'` and optional `themeMode`. If the response has `requiresEmailVerification: true` and `emailSent: true`, the app shows a "check your inbox" state with no session. Otherwise the response is an AuthResult.
- Phone OTP sign-in: `POST /auth/phone/request-otp` with `{phone}` (10 digits), then `POST /auth/phone/verify-otp` with `{phone, challengeId, otp, name?}`. The challengeId is held in memory. The resend button has a 30-second client-side cooldown.
- Email OTP sign-in and sign-up (feature flag `AuthFeatureFlags.emailOtp = true`): `POST /auth/email/request-otp` with `{email}`, then `POST /auth/email/verify-otp` with `{email, challengeId, otp, name?, phone?}`. A 404 or 501 from request-otp turns the option off for the run.
- Password reset: `POST /auth/password-reset` with `{email}`. The app requires `accepted === true` and always shows the generic "if an account exists" message.
- Booking phone verification (guest flow): `POST /auth/guest/request-otp` with `{phone}`, then `POST /auth/guest/verify-phone` with `{challengeId, phone, otp}`. The saved state comes from `GET /customer/phone-verification`.
- Session end: `POST /auth/logout` with `{refreshToken}` (best effort, errors ignored), then local state is cleared. Tokens live in secure storage and are refreshed only after a 401 (see Cross-cutting).
- Quick unlock (MPIN and biometric) is local only with no network calls (`lib/services/mpin_service.dart`, `lib/services/biometric_auth_service.dart`). Five wrong MPINs lead to `usePhoneOtpRecovery`, which signs out.

## Cross-cutting

### HTTP client, base URL and headers

- Client: `package:http` `http.Client`, wrapped by `ApiCore` (`lib/services/api/api_core.dart:14-41`). `ApiClient` (`lib/services/api_client.dart:27-40`) is the facade used by screens and providers.
- Base URL: `String.fromEnvironment('API_BASE_URL', defaultValue: 'https://urban-tanker-backend.onrender.com/api')`, trailing slash removed (`lib/services/api_client.dart:49-53`). Socket URL: `SOCKET_URL` dart-define, else the base URL minus `/api` (`lib/app/app_controller.dart:417-422`). Push: `ONESIGNAL_APP_ID` dart-define (`lib/app/app_controller.dart:57-61`).
- Headers on every backend request (`lib/services/api/api_core.dart:233-236`): `Content-Type` (application/json, or image/jpeg for the selfie), `X-Client-Platform: mobile`, and `Authorization: Bearer <access token>` when a token is stored. Yes, the app sends `X-Client-Platform: mobile`. This header is load-bearing on the server: `refreshTokenForClient` returns `refreshToken` in the JSON body only for `mobile` (`ut_landing/backend/src/routes/auth.ts:53-54`), so without it the app would have no refresh token.
- The signed-URL PUT (`lib/services/api/vendor_api.dart:285-291`) sends no bearer and no X-Client-Platform header.
- Timeouts: 20 s per request by default (`api_core.dart:106-110`); 30 s for the file PUT (`vendor_api.dart:290`). A request that runs past 3 s sets `slowRequest`, which drives a banner (`api_core.dart:24, 112-126`; `lib/app/app.dart:95-99`).

### Tokens and session (names only)

- Secure storage (flutter_secure_storage) keys: `urban_tanker_access_token`, `urban_tanker_refresh_token`, `urban_tanker_session_user` (`api_core.dart:43-65`). Android options: `resetOnError: true, migrateWithBackup: false`; iOS accessibility `first_unlock_this_device` (`lib/services/api_client.dart:42-47`).
- SharedPreferences keys: `theme_mode`, `biometric_enabled`, `biometric_prompt_offered`, `last_auth_method`. The legacy `session_user` key is migrated to secure storage once and removed (`lib/app/app_controller.dart:86-98`). No tokens are stored in SharedPreferences.
- On start, `AppController.create()` restores the session only when both the access token and the stored user are present (`app_controller.dart:81-111`).

### Refresh flow

- Trigger: an HTTP 401 on any request with `retry: true` and path not `/auth/mobile-refresh` (`api_core.dart:144-156`). The request is retried once with `retry: false`.
- Single-flight: concurrent 401s share one `_refreshOperation` (`api_core.dart:250-256`).
- On success both tokens are saved (`api_core.dart:278-280`). On any failure (no refresh token, a non-2xx, a network error, or a 5xx) both tokens are cleared (`api_core.dart:281-285`). A transient network failure during refresh therefore signs the user out on next launch.
- There is no proactive refresh before expiry, and the socket does not trigger a refresh.
- A 401 retry re-sends the POST or PATCH body once. The booking has an idempotency key, but other writes do not.

### Retry, 429 and error handling

- Transport retries are GET-only. They fire on timeouts (20 s), `SocketException`, and HTTP 502, 503 or 504, with delays of 500 ms, 1 s and 2 s (`api_core.dart:24-30, 193-220`). POST, PATCH and DELETE are never retried at transport level.
- `retry: false` only disables the 401 refresh path (`api_core.dart:144`). It does not disable GET transport retries. OTP, password reset and login are all POST, so they are never transport-retried. The public tracking GET passes `retry: false` but still retries 502-504.
- 429: no handling. `Retry-After` and `RateLimit-*` headers are not parsed. The status maps to "Too many requests. Please wait a moment and try again." (`lib/services/friendly_error.dart:43`). The OTP resend has only the 30 s client cooldown.
- Server rate limits the app can hit (`ut_landing/backend/src`): login 20/15 min per IP and 10/15 min per account (routes/auth.ts:27-28); OTP request 5/10 min (auth.ts:25) and 3/10 min per phone (auth.ts:26); phone verify 20/15 min (auth.ts:34); signup 5/15 min and 3/h per email (auth.ts:29-30); password reset 5/15 min and 3/h per email (auth.ts:31-32); quote 20/10 min (routes/customer.ts:19); delivery OTP 3/10 min (routes/customerExtended.ts:14); partner 10/h (routes/partner.ts:8); global 120/min (server.ts:65).
- Error body: the app reads `error` (string) and `details.fieldErrors` (`api_core.dart:157-189`). Non-JSON bodies give "Request failed (code)". Friendly text maps by status in `friendly_error.dart:30-47`.

### x-request-id

- The app neither sends nor reads `x-request-id`. The server echoes it on responses and generates one otherwise (`ut_landing/backend/src/middleware/observability.ts:10-16`). Error JSON includes `requestId` (`middleware/errors.ts:12`), which `ApiCore` ignores. Support tickets therefore cannot carry a request id from the app today.

### Caching and local storage

- ETag, If-None-Match, X-Total-Count and Cache-Control handling: none in `lib/`.
- In-memory caches: Riverpod `autoDispose` FutureProviders in `lib/app/providers.dart` (refetch when re-watched after dispose); `BookingsNotifier` keeps appended pages (providers.dart:60-105); HomeShell keeps the services list and the notifications future in State (home_shell.dart:48-66).
- File caches: `invoice-{id}.json` in the app documents directory (`lib/screens/invoice_detail_screen.dart:168-171`), deleted at sign-out (`lib/services/invoice_files.dart:8-21`). Temporary photos are discarded after use (`lib/services/temporary_photo.dart`).
- Images: `CachedNetworkImage` exists in `lib/core/design_system/widgets/identity.dart:55`, but no screen passes `avatarUrl`, so no backend image URLs are loaded. Map tiles come from `https://{s}.basemaps.cartocdn.com/...` (`lib/screens/common/map_tiles.dart:14`), which is not the backend.

### Pagination and full-list loads

- Offset pagination (`offset`, `pageSize`, `nextOffset`): customer bookings only. The UI loads 30 per page with infinite scroll (`providers.dart:60-105`). `bookings()` (`customer_api.dart:125-136`) loads up to 50 pages x 100 and is used only by `notification_routing.dart:63` on notification tap.
- Page-number pagination (`page`, `pageSize`, `total`): admin orders (`dispatch_screen.dart:183-211`, default 25), admin payouts (app loads page 1 only), admin audit logs.
- Vendor orders: the server supports `offset`, `pageSize` and `nextOffset` (`routes/vendor.ts:95-104`), but the app sends neither and expects a bare array (see the mismatches below).
- Everything else is a full list with no pagination. Examples: admin vendors, customers, coupons, services, partner applications, vendor fleet and payouts, notifications, support requests.

### Startup and tab-build loads

Startup performs only local reads before `runApp` (`lib/main.dart:14-25`). Firebase and OneSignal start after `runApp` (`main.dart:25-43`). Network calls then start with the session restore:

- Session restore: socket connect (app_controller.dart:418-425) and device registration via `identify` (app_controller.dart:414; `push_notification_service.dart:42-48`).
- Customer shell: `GET /customer/services` and `GET /customer/notifications` in HomeShell init (home_shell.dart:65-67). `IndexedStack` builds every tab for the role (`home_shell.dart:197-199`), so the Account tab's watched providers all fire at once: profile, usage, membership, offers (`customer_account_screen.dart:23, 54, 724, 804`), and the `_AccountSection` widgets that call their provider in build (`customer_account_screen.dart:975-976`): wallet, invoices, subscriptions, contracts, addresses and support. The Overview and Bookings tabs watch `bookingsProvider` (page 1 of 30; `customer_overview.dart:42`, `bookings_screen.dart:51`).
- Vendor shell: `GET /vendor/notifications`; operations watches vendor orders in build (`vendor_operations_screen.dart:61`), fleet watches the dashboard (`vendor_fleet_screen.dart:22`), earnings watches payouts (`vendor_earnings_screen.dart:33`). Vendor orders is a full, unpaginated list.
- Admin shell: `GET /admin/notifications`; the pulse watches health (`admin_pulse_screen.dart:15`); the Operations tab sections load their lists on setup (`people_section.dart:46-49`, `finance_section.dart:43-45`, `setup_section.dart:33, 350`).
- Dispatcher shell: the live board watches page 1 of admin orders (`live_screen.dart:52`), the dispatch board watches orders and vendors (`dispatch_screen.dart:41-42`), and the alerts screen watches alerts (`alerts_screen.dart:57`).

| public_tracking_screen.dart:37, 70-74 | 30 s | GET /public/tracking/{token} | Always while the screen is open and foregrounded; restarted on resume |
| order_actions_sheet.dart:38, 341-344 | 15 s | POST /vendor/location (latest fix only) | While location sharing is active; no send without a new fix |

- No timer on the dispatcher board, the vendor operations list or the admin pulse. Those refresh on pull-to-refresh, after own actions, or on realtime events (vendor only).
- Duplicate refresh: while booking details is open, `booking.updated` and `notification.created` are handled by both HomeShell (home_shell.dart:71-79) and BookingDetailsScreen (booking_details_screen.dart:105-110), so the same bookings provider is invalidated twice per event.
- The customer bookings list does not refresh on resume and has no poll. If the socket is down, the list stays stale until pull-to-refresh or the next event.

### Realtime behaviour

- Connection: one socket per session, created in `_setSession` (`app_controller.dart:418-425`), with a fresh token on every (re)connect (`realtime_service.dart:35-39`). Reconnection is automatic up to 10 attempts; after that the app reconnects only on resume (`realtime_service.dart:16, 40-43, 95-98`).
- Background: `paused` disconnects (`lib/app/app.dart:66-68`); `resumed` calls `resume()` (`app.dart:69-70`).
- Reconnect after refresh: no explicit reconnect or re-auth. The live socket keeps its old handshake. A later reconnect reads the stored token, so it picks up a refreshed token only if a refresh already happened. If the stored token expired while disconnected, the handshake fails ("Invalid session" from the server, `backend src/server.ts:84-95`) until an HTTP 401 refresh rotates the token. Verify on a device.
- Rooms: the server auto-joins `customer:{userId}` on connect (src/server.ts:107), `vendor:{vendorId}` for vendor accounts (src/server.ts:118) and `admins` for admin accounts (src/server.ts:117). The app joins only `booking:{id}` rooms, and rejoins them after reconnect (realtime_service.dart:51-54).
- Delivery gaps (server behaviour, cross-checked): `booking.updated` goes only to `booking:{id}` and `admins` (services/realtime.ts:33-41), so customers on the list and vendors never receive it. Customer cancel and reschedule emit no realtime event (`routes/customerExtended.ts:18-19`, `services/bookingLifecycle.ts:19-22`), so vendors are not notified live; DB triggers, if any, were not verified. The dispatcher board has no realtime listener at all, so admin `booking.updated` events only invalidate the bookings provider, which the dispatcher does not watch.

### App-vs-server mismatches (verified against ut_landing/backend/src)

1. GET /vendor/orders: the app requires a bare JSON list (`vendor_api.dart:26-29`, `parseList`), but the server returns `{rows, nextOffset}` (`routes/vendor.ts:103`). The vendor operations list and order actions would fail with "The vendor orders response was invalid." Verify against the deployed server.
2. POST /customer/coupons/validate: the app requires a `coupon` object (`customer_api.dart:436-440`); the server returns `{valid: true}` (`routes/customer.ts:87`, `routes/customerExtended.ts:34`). A valid code therefore always fails in the booking form.
3. POST /customer/orders/{id}/rating with a blank review: the app sends `"review": null` (`booking_details_screen.dart:506`), and the server schema rejects null (`routes/customerExtended.ts:20`), returning 400 "Invalid rating".
4. Email OTP: `/auth/email/request-otp` and `/auth/email/verify-otp` have no server route (routes/auth.ts has only /guest/* and /phone/*). The app turns the option off on 404 or 501 (`app_controller.dart:161-172`), so the failure is hidden at runtime.
5. Three listened events have no emitter: `booking.rejected`, `booking.vendor_accepted` and `booking.delivered` (`home_shell.dart:73-75`). They appear only as analytics names (`src/lib/analytics.ts:35-37`).
6. `booking.updated` reaches only the booking room and admins (see Realtime). Vendors' order list relies on `vendor.order.*`, which covers created, taken and declined, but not customer cancellations.
7. Customer cancel and reschedule emit no realtime event or notification (see Realtime).
8. `vendor:join` is never emitted by the app, but the server auto-joins the vendor room anyway, so nothing breaks.
9. POST /vendor/drivers sends `mobileE164` unnormalised (`vendor_api.dart:84`); the server validates it with a digit regex (`routes/vendorExtended.ts:131`). Check that the form normalises before calling.

### Unused endpoints (no caller in lib/)

- Admin: GET, PATCH and DELETE `/admin/vendors/$id`; GET, PATCH and DELETE `/admin/customers/$id`; PATCH and DELETE `/admin/coupons/$id`; PATCH `/admin/payouts/$id/status`; PATCH `/admin/partner-applications/$id`. These are 10 endpoints, and the list-level calls for the same resources are used.
- Vendor: POST `/vendor/offline-mutations` (queueVendorMutation) and POST `/vendor/offline-mutations/$id/retry` (retryVendorMutation). The offline queue is read and discarded only. Queueing would first re-fetch the whole queue for dedupe (`vendor_api.dart:432-454`).

### Auth flows that must stay unchanged

See the auth section above. The flows are password sign-in (`/auth/login`), email sign-up (`/auth/signup`), phone OTP sign-in (`/auth/phone/*`), email OTP (`/auth/email/*`, runtime-disabled on 404 or 501), password reset (`/auth/password-reset`), guest phone verification (`/auth/guest/*`), logout (`/auth/logout`) and refresh (`/auth/mobile-refresh`). All OTP and reset calls use `retry: false`.
