1. Summary

The application is feature-rich and mostly complete for a first release. The customer-facing site, the booking flow, the vendor, admin and customer portals, and the backend API all exist. The main risks are not missing features. They are security hygiene (credentials in files), correctness in a few portal views, and operational gaps that must be closed before launch.

This pass moved the user-visible text of the whole web app into typed content modules under src/content/, in the style of AEM content fragments. Rendered output is unchanged for the public screens, and every plain-text literal from the portal screens was found verbatim in the content layer.

2. Architecture

Frontend (ut_landing/src)

  • React 19 and TypeScript on Vite 8. Screens are chosen by a Zustand navigation store, not URL routes. The only path-based route is /track/<token> for public tracking.
  • Screens are lazy-loaded. A chunk-reload guard now handles stale chunks after a deploy.
  • Data comes from React Query over a typed API client (src/api). Realtime uses socket.io-client with a reconnecting client (src/services/realtime.ts).
  • Auth state lives in a Zustand store. The refresh token is an HttpOnly cookie.
  • Leaflet and OpenStreetMap for maps and geocoding. Razorpay checkout is loaded from its CDN.
  • Offline support: a service worker and a vendor mutation queue (src/services/offlineMutationQueue.ts).
  • Styling is SCSS, split across roughly 30 partials, several of them with minified one-line rules.

Backend (ut_landing/backend)

  • Express 5 with helmet, CORS allow-list, compression, a global rate limiter, and an observability middleware that writes JSON logs.
  • Supabase for auth, storage and Postgres (via the pg pool and supabase-js). Schema is in backend/supabase/001_initial.sql with an incremental update block.
  • Integrations: Razorpay (order, verify, webhook, refund), MSG91 or Twilio for SMS, SMTP for email, OneSignal and web push, analytics with retention and anonymisation.
  • Background sweeps run every 15 minutes: booking reminders, document expiry, storage cleanup and analytics retention.

Hosting

  • Frontend on Hostinger (public_html, with public/.htaccess for routing, headers and CSP). API on Render (render.yaml). Mobile app on the stores.

4. Content Migration (AEM-Style Layer)

Every user-visible literal in the web app is now held in a typed content module under src/content/. Components import the module and render its values. The modules are plain TypeScript objects declared as const, so a missing key fails the typecheck. Lists are arrays of objects with an id, and dynamic text is a function. Emphasis splits into separate keys, so the markup stays in the component.

Verification

  • Rendered text, public screens: ten screens captured at 390 px and 1280 px before and after the migration. All 20 captures match exactly.
  • Portal literals: 561 plain-text literals from the original portal files were checked. All 561 are present verbatim in the content modules.
  • Build and checks: typecheck, lint, 15 frontend tests and the production build pass. No display text is left in the screens or components, apart from data values the code compares against (status codes and similar).

Not yet in the content layer

  • The backend's own user-facing text: email and SMS templates, and API error messages shown in the UI.
  • The 54 legacy HTML pages in public_html/. These are static files and are not part of the React build.
  • The Flutter mobile app's text, which has its own copy of the strings.
  • Status codes are still raw codes in some live views (for example pending_vendor, en_route), since no label map exists for them.

Trade-offs

  • The content is compiled into the bundle. A change needs a rebuild and deploy, not an editor in a CMS. Moving to a headless CMS later means replacing the module imports with a loader. The keys are already in place for that.
  • There is no locale support yet. Adding a second language would mean one module per locale, with the same keys.

Correctness (reported by the migration review, not fixed)

  • Tracking: a failed background refetch replaces an open tracking view with the error state, because query.isError is checked before query.data.
  • Customer operations: Title Case comparisons ('Delivered', 'Cancelled') never match the lowercase live codes. As a result, Rate is always disabled and Cancel is never disabled in live mode.
  • Live statuses: customer, dispatch and notification views show raw status codes with no label mapping.
  • Admin workspace: the vendors, drivers, customers and fleet items return early, so their dedicated views are unreachable. In demo mode, fleet renders the vendor list.
  • Dates: toISOString() on local midnight shifts the date by one day in IST. This affects the finance settlement start date and the default report range.
  • Vendor fleet: capacity is labelled "KL" but saved as litres.
  • Partner form: the partner type and availability values submitted to the API are the English labels, not codes.
  • Invoices: the "Total paid invoices" label counts all invoices.
  • Dead code: CustomerTracking, CustomerMembership and CustomerAddresses are not reachable from the workspace.
  • Coupons: the "expiring this period" count uses a hard-coded date of 2026-12-31.
  • Booking: the review step formats the amount with toLocaleString, while the summary uses Intl currency formatting, so the two can differ.
  • Footer: "Empty tanker hire" in the footer and "Empty tanker transport" in the header dropdown.
  • Home: detectLocation checks the loading state from the render closure, so two quick calls can get past the guard.

Reliability and operations

  • Fixed in this review cycle: dev proxy port mismatch, trailing slash in FRONTEND_ORIGIN, stale chunks after deploy, the duplicated backend test run, and the blank-value config crash.
  • The advisory lock for background sweeps has not been run against a live Postgres.
  • Two development fallbacks point at localhost in the frontend source and need a review before release.

Maintainability

  • Many screens and SCSS partials were written as one-line blocks, which makes review and diffs hard. The content migration has split the screen files, but styles are unchanged.
  • Line endings are mixed across the tree (CRLF and LF), which adds noise to diffs.
  • Unused dependencies: @vis.gl/react-google-maps is installed in the web app but not used.
  • Two public folders: public/ for the React build and public_html/ for the legacy reference site. This is easy to confuse.
  • Only five frontend test files exist, and there are no component or screen tests. The portal screens were verified by static checks and the typechecker, not by behaviour tests.
  • The git index holds staged versions of some edited files that differ from both HEAD and the working tree. Clear the index before committing.

6. Recommendations

  1. Now: revert the database URL in backend/vitest.config.ts, rotate the credentials listed above, and remove the demo credentials from source.
  2. Before launch: fix the portal correctness items, starting with the customer status comparison and the admin workspace early returns. Add behaviour tests for those views.
  3. Before launch: resolve the cross-site cookie with an API subdomain, and run the Playwright suite against staging.
  4. Next: move the backend's email and SMS templates into content, and decide on the status label map for live views.
  5. Next: add component tests for the portal screens, and tidy the SCSS and line endings.
  6. Later: add a Redis adapter and rate-limit store before scaling beyond one instance, and move the content layer to a headless CMS if the content team needs to edit it directly.

7. Limits of This Analysis

  • Behaviour was checked for the public screens only, using browser captures. Portal screens were checked by static comparison and the typechecker, because they need signed-in accounts.
  • The Flutter app and the backend's templates were not reviewed in detail.
  • No changes were committed.
