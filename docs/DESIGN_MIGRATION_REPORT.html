Frontend, backend, route and design migration

Implementation report for the React/Vite application and the supplied public_html design references.

Architecture

Frontend

React 19 + TypeScript + Vite. Zustand owns SPA screen state. SCSS is composed through src/styles/app.scss.

Backend

Express + TypeScript + Supabase service-role API. Role authorization is enforced by middleware and server routes.

Reference site

Original public_html files remain intact and are served independently on port 4174.

SPA and navigation

Browser path or deep link→React SPA shell→Zustand screen state→Role workspace when authenticated

Existing browser paths and client-side navigation are preserved. React navigation does not mutate the address bar. The separate reference server retains its original .html URLs.

Security hardening

Authentication and roles

Bearer tokens are validated server-side. Customer, vendor, dispatcher, and admin access is checked before protected operations; partner review endpoints are admin-only.

Abuse controls

Login, OTP, analytics ingestion, and partner applications use endpoint-specific throttles in addition to the global API limiter. Socket.IO booking joins are bounded per connection.

Data protection

Authenticated direct write grants were removed from the canonical SQL. RLS remains enabled, service-role access is server-only, and upload type, extension, size, and user-scoped paths are validated.

Session safety

Refresh tokens stay in HttpOnly cookies and are no longer returned in JSON responses. Password reset redirects use the configured frontend origin.

Partner endpoint

Partner service selections are allowlisted, applications are validated server-side, and application review is restricted to admins.

Operational action

Credentials found in local environment files must be rotated before production deployment; source code cannot safely rotate hosted provider secrets.

Security features added

Secret-free PHP configuration

Legacy PHP configuration files now load APP_SETUP_KEY, APP_SECRET, DB_USER, and DB_PASSWORD from the runtime environment instead of storing credentials in source.

Fail-closed startup

Missing required PHP environment values raise an explicit runtime error rather than silently starting with incomplete security configuration.

Credential removal

The local backend environment file containing Supabase, payment, and messaging credentials was removed from the workspace. Secret values were searched for and verified absent.

Deployment controls

Hostinger guidance now documents secret injection, private configuration placement, deployment exclusions, credential rotation, and disabling the initial setup endpoint after administrator creation.

Security assessment update

A read-only repository assessment reviewed frontend inputs, backend APIs, legacy PHP routes, role boundaries, database access, uploads, payment callbacks, realtime authorization, security headers, and deployment configuration. One high-confidence issue was identified and remediated in source: production-looking credentials and encryption/setup secrets were present in local deployment artifacts.

Hardcoded PHP database, setup, and encryption values replaced with required environment variables
Local backend credential file removed from the workspace

Analytics

Browser event→Session ID in sessionStorage→POST /api/analytics/events→analytics_events table→Admin summary/export
  • Frontend events are emitted through trackEvent and carry bounded string, number, and boolean properties.
  • Event names are schema-validated; property values are capped and each event accepts at most 20 properties.
  • Analytics ingestion is rate-limited and failures do not block customer workflows.
  • Admin-only summaries calculate login, booking-started, booking-created, vendor-accepted, and delivered funnel rates.
  • Retention and anonymization jobs protect older session identifiers according to backend configuration.

Analytics event triggers

Events are emitted after meaningful user or booking state changes. Client events use trackEvent; server lifecycle events use recordAnalyticsEvent. All events are validated before storage in analytics_events.
