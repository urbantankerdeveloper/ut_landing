1. Executive Summary

Status update (2 Nov 2026): the blockers and high-risk items are remediated in code for the split hosting setup (Hostinger frontend, Render API). Sections 2 to 4 give the current state. The sections marked "initial review" describe the original findings. Launch still needs the external inputs and decisions listed in section 4.

The code base is close to deployable as a build. The frontend type-checks and builds, the backend type-checks, and the unit tests pass. The remaining work is mostly external: provider credentials, live Razorpay and SMS validation, and staging checks. That is consistent with the latest backlog.

Six items must be settled before a production go-live. The first is that the deployment topology is not decided. The repository references Render, Hostinger, and Netlify at the same time, and the domain is inconsistent. The others are a broken lint gate, uncommitted dependency changes, a default Content Security Policy that will likely block the Razorpay checkout script, two backend dependency vulnerabilities, and backend tests that fail without environment variables.

Two security settings need attention before launch. USE_DEFAULT_VERIFICATION_CODE must be false in production, and the database connection currently disables TLS certificate verification.

6. Go-Live Blockers (initial review)

These must be resolved before a production deployment. They are ordered by severity.

  1. B1Deployment topology is not decided. The repository points at several hosts at once. .env.production sets the API to https://urban-tanker-backend.onrender.com. package.json has a build:hostinger script. public_html/netlify.toml and public/_headers are Netlify artifacts. The CORS allow-list in backend/src/server.ts includes urbantanker.in, while the canonical link in index.html is urbantanker.com, which appears 18 times against 6 for .in.
    Impact: VITE_API_BASE_URL and VITE_REALTIME_URL are baked into the bundle at build time. CORS, cookie domains, Supabase redirect URLs, and the Razorpay webhook URL all depend on this choice. Also, public_html/netlify.toml publishes the legacy static prototype, not the React app.
    Decision needed: choose one of (A) Express serves the SPA and API from one host, or (B) a static frontend host with a separate API host. Then set the domain and VITE_* values to match.
  2. B2The lint gate is broken, probably by an uncommitted change. The working-tree package.json lowers @eslint/js from ^10.0.1 to ^9.39.5 and typescript-eslint from ^8.69.0 to ^8.14.0, while ESLint resolves to 10.14.0. That version mismatch matches the crash.
    Action: restore the committed versions or align @eslint/js to the ESLint 10 line, then re-run npx eslint .. This has not been tested yet.
  3. B3Uncommitted dependency changes are unreviewed. jspdf moves from ^2.5.2 to ^4.2.1, a major version change. It is used by src/utils/pdf.ts for invoices and PDFs. package-lock.json has a 2,952-line insertion and a 1,652-line deletion.
    Action: verify generated invoice and contract PDFs against the current output, then commit package.json and the lock file together so the build is reproducible.
  4. B4No custom Content Security Policy, so the Helmet default applies. backend/src/server.ts calls helmet() with no options. When Express serves the SPA, the default policy sets script-src 'self' and img-src 'self' data:. Those directives would likely block the Razorpay checkout script loaded in src/hooks/useFrontendFeatures.ts and the external map tiles.
    This is not yet confirmed in a browser. Action: define a CSP that allows checkout.razorpay.com, Google Fonts, the OpenStreetMap tile and Nominatim hosts, and the Socket.io connection, then check it in staging. The backlog item "CSP review" also remains open.
  5. B5Backend has production dependency vulnerabilities. body-parser (high) and qs (moderate) are both reported by npm audit --omit=dev. The Express request body parser depends on them.
    Action: run npm audit fix in backend/, re-run the backend tests, and commit the updated lock file.
  6. B6Tests and CI are not deployment-ready. Backend tests fail at import unless SUPABASE_URL and a service-role key are set. There is no .github/ directory, so no pipeline runs the build, tests, or audit. The backend lint script refers to ESLint, but ESLint is not installed in backend/.
    Action: add a Vitest setup file or .env.test that stubs the required variables, add a CI workflow with build, test, audit, and smoke steps, and make the Playwright base URL configurable.

7. High-Priority Risks (initial review)

  1. H1A fixed verification code can bypass guest booking OTP. When USE_DEFAULT_VERIFICATION_CODE=true, SMS is skipped and DEFAULT_VERIFICATION_CODE is accepted. The fallback value is 123456. The default for the flag is false, but nothing stops production from enabling it.
    Action: set it to false on the host. Add a startup guard in backend/src/config.ts that refuses to start when NODE_ENV=production and the flag is true.
  2. H2The database installer is destructive, and the README points to a missing file. backend/supabase/001_initial.sql contains 21 DROP statements. It is the canonical installer, which resets the public schema. db:migrate and db:reset both run reset-database.ts. The script is guarded by CONFIRM_DATABASE_RESET=URBAN_TANKER_RESET. The README tells operators to apply backend/supabase/012_booking_service_details.sql, which does not exist.
    Action: never run the installer against a database with data. Add numbered, forward-only migrations for production. Rename db:migrate so it does not suggest a safe migration. Take a backup before any schema change.
  3. H3Database TLS certificate verification is disabled. backend/src/database.ts sets ssl: { rejectUnauthorized: false }. That permits a man-in-the-middle on the Postgres connection.
    Action: pin the Supabase CA certificate and set rejectUnauthorized: true, or confirm with the provider that this is acceptable.
  4. H4The backend assumes a single instance. Socket.io uses the default in-memory adapter, with no Redis adapter in the dependencies. Background jobs in backend/src/services/jobs.ts run on setInterval with no advisory lock. The express-rate-limit store is in memory.
    Impact: scaling past one instance would duplicate jobs and notifications, drop realtime events, and make rate limits per instance. Action: run one instance at launch, or add a Redis adapter and Postgres advisory locks first.
  5. H5Configuration has drifted from the schema. WHATSAPP_FROM_NUMBER, SUPABASE_JWKS_URL, and SUPABASE_PUBLISHABLE_KEY appear in backend/.env.example but are not used in backend/src. RAZORPAY_WEBHOOK_SECRET is read directly from process.env and is not in the zod schema. SUPABASE_URL, SUPABASE_DB_URL, DB_POOL_MAX, and SUPABASE_SERVICE_ROLE_KEY each appear twice in .env.example.
    Action: add every required variable to the zod schema so missing values fail at startup, remove unused keys, and de-duplicate the example file.
  6. H6Deployment scaffolding is missing. There is no Dockerfile, Procfile, render.yaml, .nvmrc, or engines field. Development uses Node v26.13.0, which has not been checked against the host. The start script runs db:check before the server, so a database outage stops the process from starting. That is reasonable, but it should be expected by the host's restart policy.
    Action: pin a supported Node LTS in engines and .nvmrc, and document the start command, health check paths, and restart behaviour.
  7. H7Status documents disagree. docs/IMPLEMENTATION_BACKLOG.md lists 33 items, 28 IN PROGRESS and 5 PENDING. docs/IMPLEMENTATION_BACKLOG.html lists 15 items, all EXTERNAL, and is dated 15 October 2026. The Markdown version still lists Razorpay webhook verification as missing, but backend/src/routes/payments.ts implements an HMAC-verified webhook.
    Action: keep one backlog as the source of truth. This report uses the 15-item HTML view, checked against the code.

10. Recommended Deployment Sequence (Split: Hostinger frontend, Render API)

  1. Confirm the open decisions. Final domain, and whether to use an API subdomain (section 11).
  2. Provision the database. Create the production Supabase project. Copy its CA certificate for DB_SSL_CA. For an empty project, apply the full installer once; for an existing database, use npm run db:update. Never run db:reset against data. Enable backups.
  3. Deploy the API to Render. Create the service from render.yaml. Enter the dashboard secrets, set FRONTEND_ORIGIN, and deploy. Confirm GET /health and GET /health/ready.
  4. Build the frontend. Run npm ci and npm run build from the repository root. This reads .env.production.
  5. Upload to Hostinger. Copy the contents of dist/ into public_html, including .htaccess.
  6. Check the headers and routing. curl -I https://<domain>/ should show the CSP and X-Frame-Options. https://<domain>/track/test should return the app shell. https://<render-host>/api/admin/orders without a token should return 401.
  7. Connect the providers. Register the Razorpay webhook at https://<render-host>/api/payment/razorpay/webhook. Add https://<domain>/login to the Supabase Auth redirect list.
  8. Smoke test in a browser on the live domain. The landing page loads. Login, refresh and booking work. The console shows no CORS or CSP errors. Run a Razorpay test-mode payment. The live tracking map and realtime updates connect.
  9. Rollback plan. Keep the previous dist/ upload so it can be restored. In Render, roll back to the previous deploy. Take a database backup before every schema change.
