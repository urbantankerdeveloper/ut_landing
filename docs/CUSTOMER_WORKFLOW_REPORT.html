Customer Workflow: Login to Delivery (End to End)

Urban Tanker customer journey across the Flutter mobile app, the Express backend, and the vendor/dispatch side it hands off to.

1. Overview

A customer signs in on the mobile app, requests a water tanker delivery, pays (wallet, online, or cash on delivery), and the booking then moves through vendor acceptance, travel, arrival, and delivery confirmed by an OTP. The customer can track the order live, reschedule or cancel it early, and rate it afterwards.

After sign-in

  • The session is restored, and the saved theme (light, dark, or system) is applied from the server.
  • The customer sees three tabs: Overview, Bookings, and Account.
  • Every app request carries X-Client-Platform: mobile. The backend reads it at signup, whether by email or by phone OTP, and stores it as the signup channel (signup_platform). Accounts created before this change have no channel recorded.
  • New mobile customers take a selfie with the front camera, or choose a JPEG from the phone's gallery, before the home screen opens. The app sends the JPEG to POST /customer/profile/selfie. The API stores it in the private customer-selfies bucket as <customer id>/selfie.jpg and records the path on the profile. Admins can open it from the customer record through a link that expires in 5 minutes, and each view is logged. Customers can fetch their own link with GET /customer/profile/selfie. A retake replaces the previous selfie, so no history is kept. The app asks for camera or photo access before it opens either one, and offers Open settings if access was turned off. On the web signup form the photo is optional. It is sent with the signup request and saved once the account is created. If the photo cannot be saved, the signup is rolled back so the customer can try again.

4. Booking Creation

Steps in the app

  1. Select services: pick one or more services. Each has its own details (water type, tanker count, capacity).
  2. Shared details: booking phone number, delivery location, delivery date, access notes.
  3. Delivery location: choose a saved address, use current location, or use coordinates. Addresses are limited to Chennai.
  4. Quote: POST /customer/orders/quote returns the price, and the quote preview runs as the user edits.
  5. Coupon (optional): POST /customer/coupons/validate.
  6. Payment method: Wallet, Online payment, or Cash on delivery.
  7. Review, then Confirm booking and Submit booking.

Backend on submit

  • POST /customer/orders validates the booking, checks phone verification for the services, and finds nearby approved vendors.
  • The booking is saved with status pending_vendor through the create_customer_booking function. It is idempotent on idempotency_key, so a retried submit does not create a duplicate.
  • For online and COD payments, a payment record is created (COD is pending with provider cash_on_delivery).
  • Nearby vendors are notified, and the customer gets a booking.created realtime event with the booking reference (for example UT-12345678).
  • The booking contact number gets a booking confirmation SMS (template guest_booking_confirmation, see Section 11).
  • The booking stores customer_type: guest when the account came from guest checkout (username starts with guest_), otherwise registered.
  • The app shows Booking submitted.

7. Tracking and Notifications

  • Bookings tab: each booking shows reference, service, capacity, delivery date, quoted amount, payment status, and current status.
  • Live tracking: Live badge and Waiting for vendor location or Vendor location available. Refresh with Refresh tracking. Realtime events (booking.updated, booking.vendor_accepted, booking.delivered) update the list.
  • Tracking link: the vendor acceptance SMS contains a link to /track/<token>. Someone without an account can follow the booking. On a phone, the page first asks Open in Urban Tanker app or Continue in browser. The browser opens the public tracking page, which shows the current status, expected delivery, vehicle and driver (or Not assigned), vehicle location on a map, and the status timeline. The app opens the same details from the urbantanker://track/<token> link, with the vehicle on a map. Both refresh every 30 seconds. Desktop browsers go straight to the tracking page.
  • Notifications: pushed for each status change. Read state and preferences are managed in /customer/notifications and /customer/notification-preferences.

9. Delivery Completion

  1. The vendor reaches the location and the booking moves to arrived.
  2. The customer taps Request delivery OTP. A 6-digit code is generated with an expiry, and it is sent by SMS to the customer's profile phone (see Section 11). If the SMS cannot be queued, the request fails and the customer can retry.
  3. The customer gives the OTP to the driver. The vendor enters it through POST /vendor/orders/:id/delivery/verify.
  4. On a valid OTP the booking moves to delivered, the payment is settled (COD collected), and the customer gets a booking.delivered notification and a delivery confirmation SMS (see Section 11).
  5. The customer is prompted to Rate delivery. The app shows Thank you for rating the delivery.
Verify the COD settlement step against the vendor delivery code before release. This review confirmed the OTP check and the delivered transition, not the exact settlement code.

11. SMS Notifications (MSG91)

SMS goes through MSG91 by default. Set SMS_PROVIDER=twilio to send the same messages through the existing Twilio setup instead. Each message is a DLT-approved template, keyed by the variables shown.

For booking confirmation, vendor acceptance, and delivery confirmation, a failed send is logged and does not block the booking or the delivery. The delivery OTP request returns an error if its SMS cannot be queued, so the customer can retry. With SMS_PROVIDER=msg91, a missing template ID means the message is not sent. There is no automatic Twilio fallback.

Template storage and admin management

Each message above is stored as a row in the sms_templates table. The backend reads templates from the database and caches them for 5 minutes. Each row has a body with {{variable}} placeholders, an active flag, and an optional MSG91 template ID. For the six built-in messages, a blank MSG91 template ID falls back to the MSG91_TEMPLATE_ID_* value in the environment config.

Admins manage templates on the new SMS templates screen in the admin workspace. The screen lists every template. Its add/edit dialog changes the body, the active flag, and the MSG91 template ID. The admin API is GET, POST, and PATCH under /api/admin/sms-templates, and every change is written to the audit log. The API rejects a body that uses a placeholder the built-in message does not allow. Saving a change clears the cache on the instance that handled it. Other instances pick up the change within 5 minutes.

Custom templates

Admins can add a new template with its own key and MSG91 template ID. The backend can send it with sendTemplateSms(key, phone, variables). The send is refused if the template is inactive or missing, if the MSG91 ID is blank, or if a placeholder has no value. It returns a result and does not throw. A custom template is sent only where the code calls it with that key. No screen in the customer workflow sends custom templates yet.
